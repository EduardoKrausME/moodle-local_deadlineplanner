# Planning architecture and threat model

The plugin uses explicit providers implementing `deadline_provider_interface`. Providers return opening, due, closing and cutoff epochs separately. Assign extensions are obtained from the dedicated extension flag; quiz overrides use Moodle's `quiz_update_effective_access`. Each provider must be independently tested against supported Moodle releases before supporting automatic modifications.

`calendar_data_service` stores non-personal module snapshots, keyed by CM, and refreshes via cron and module lifecycle events. The request-time `learner_workload_calculator` derives visibility using learner-specific modinfo and the learner's own capability, then calculates local calendar days in the learner's timezone. It does not persist identity-level workload data. `policy_evaluator` uses deterministic and institution-configurable counts and indicative weights. `conflict_detector` compares before and proposed windows. `privacy_guard` blocks small cells and only exposes approximate bands; this is a defense in depth, not a formal differential privacy guarantee.

`scenario_simulator` persists only a scenario and its sanitized aggregate. A reviewer must separately hold local apply and core module-edit rights, and `date_adjustment_service` rejects proposals if any relevant live date changed. As verified module update APIs were not available in this development environment, the only authorized application path in this release is the native Moodle activity editor. No UPDATE SQL touches module dates.

Threats: unauthorized student/hidden activity disclosure, cross-course inference by differencing, lost updates, CSV formula injection, suspended enrollments, availability drift, DST ambiguity, stale snapshots, denial of service from large cohorts, and unbounded aggregation. Mitigations include strict context checks, k-threshold suppression, coarse ranges, user visibility checks, optimistic fingerprints, CSV quoting/prefixing, finite enrolment limits, periodic refresh and no personal workload persistence. Institutional review is required before deploying in high-stakes or small-cohort situations.
